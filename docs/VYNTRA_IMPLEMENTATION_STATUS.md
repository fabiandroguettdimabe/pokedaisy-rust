# Estado de implementación de Vyntra

Actualizado: 2026-11-16. Este documento registra el comportamiento comprobado del checkout; una función no se considera disponible por aparecer en una imagen de referencia o una etiqueta de interfaz.

## Avance de migración y propiedad de sesión (2026-11-16)

- **T04 parcial:** `desktop-rust/crates/pokedaisy-desktop/src/migration.rs` ofrece preview de solo lectura, journal JSON versionado con copia de respaldo, copia por staging y verificación SHA-256. El Vault permite revisar y aplicar SRAM heredada no ambigua; los estados sin identidad quedan bloqueados y los originales se conservan. Los conflictos de destino se presentan antes de aplicar. Todavía no hay descubrimiento fuera de las carpetas configuradas ni fault injection.
- **T08 parcial:** las acciones Play nuevas usan `storage_id` derivado del contenido y el shell vuelve a resolver ese ID antes de iniciar; el índice numérico queda como compatibilidad con clientes antiguos. El player retiene ROM activa y hash del core al iniciar, y las rutas de autosave, SRAM, estados y cierre usan esa identidad. No se probó con un core real ni se completó el protocolo continuo Player–Companion.
- **T05 parcial:** F4 solo pasa el estado al core si el manifiesto confirma tipo, estado committed, ROM, hash del core, formato, tamaño y SHA-256. Estados legacy o alterados quedan bloqueados con explicación. Aún falta restauración con rollback, auditoría SRAM legacy y fault injection.
- **T06 parcial:** el Core Manager valida cabecera PE, arquitectura y exports sin ejecutar la DLL; una acción explícita lanza un proceso hijo oculto con timeout de ocho segundos para comprobar ABI y `retro_get_system_info`. Caídas, DLL inválida y timeouts vuelven como reporte sin bloquear la ventana. Falta probar con un core fixture real y dependencias faltantes.
- **T03 parcial:** `inspect.rs` valida cabeceras básicas GB/GBC/GBA/DS con lectura acotada y marca identidad como parcial; el catálogo usa metadatos inspeccionados. La ROM se vuelve a hashear antes de Play y se rechaza si cambió desde el último catálogo. Falta corpus amplio de headers/checksums y deduplicación visible.

## Cambios implementados en este checkout

- Desktop se muestra como **Vyntra Desktop** y usa la paleta Dark Crimson + Black en su interfaz SDL. El símbolo V se dibuja como vector en SDL; las variantes SVG original, reducida y monocromática están en `desktop-rust/assets/`.
- Android muestra **Vyntra Pocket** como nombre de aplicación. Se conservan `applicationId` y `namespace` `com.pokedaisy.app` para no romper actualización in-place ni acceso a los datos existentes.
- Los paquetes Rust propios se llaman `vyntra-desktop` y `vyntra-libretro`; las rutas en disco aún conservan `crates/pokedaisy-*`.
- Desktop prefiere `VYNTRA_CORE_DIR`; conserva `POKEDAISY_CORE_DIR` como alias legado y solo escribe el aviso de deprecación en builds debug. Busca primero nombres `vyntra_*_libretro` y mantiene los nombres `pokedaisy_*_libretro` como fallback.
- Ajustes distingue `No instalado` de `Archivo detectado · sin probar`. La DLL se carga al iniciar un juego mediante `LibretroCore::load`; errores de exportaciones/API/carga se notifican en ese flujo. Un archivo presente no se anuncia como listo.
- La pantalla Companion de Desktop informa explícitamente qué paneles aún no están implementados.
- Inicio de ejecución del plan técnico (`docs/VYNTRA_PLAN_TECNICO.md`): se añadió `docs/vyntra-capabilities.md` (matriz baseline de evidencia, T01/QA-02) y se incorporaron scaffolds `domain.rs`/`protocol.rs` en `desktop-rust/crates/pokedaisy-desktop/src/` (tipos de dominio/contrato versionado y errores, base para INFRA-01/T02) sin cambiar el comportamiento actual del emulador.
- Verificación Desktop (2026-11-16, `desktop-rust/`, Rust `cargo 1.100.0` / `rustc 1.100.0`): `cargo fmt --all --check` OK; `cargo check --workspace`/`cargo check -p vyntra-desktop` OK con warnings `dead_code` esperados en scaffolds aún no integrados; `cargo test --workspace` OK (19 tests en `vyntra-desktop`: `domain`, `protocol`, `identity`, `library`, `shell`, `settings`, `main`; 0 en `vyntra-libretro`; 0 doc-tests). No se probó runtime/emulación.

  - **WIN-LIB-03/T11 intake (HECHO-PARCIAL):** multiarchivo valida ROM por estructura, rechaza ausentes/incorrectas, deduplica rutas canónicas y reporta conteos vía ACK/UI. Tests agregan GBA sintética válida, ROM falsa, duplicado y ausencia. ZIP con cuotas, progreso y cancelación siguen pendientes.

Scopes/perfiles y resolución de conflicto multi-ventana siguen pendientes.
  - **NEW-DEV-01/T14 + CMP-DEX/BATTLE/T15 (HECHO-PARCIAL):** `type-chart-gen3.json` se deriva de las tablas Kotlin, incluye schema/dataset/source hash/license y tiene consumidor Rust probado; CI verifica paridad. Companion calcula enfrentamientos Gen 3 con uno o dos tipos, identifica su dataset y advierte que hacks pueden variar; faltan Dex y datasets adicionales.
  - **MULTI-03/07/T10 (HECHO-PARCIAL):** `transport.rs` implementa snapshots latest-only limitados a 256 KiB, ligados a sesión/epoch/revisión, y comandos con cola acotada donde Stop se entrega fuera de banda. Cuatro pruebas verifican consumidor lento, snapshots viejos/grandes, cola llena y prioridad de Stop. La comunicación real launcher–Player por named pipe Windows aún no está conectada.
  - **INFRA-01/T02 (parcial):** `shell.rs` ahora parsea acciones IPC con `protocol::parse_legacy_action` (límite de payload/validación JSON), emite `UiAck`/`AppError` al frontend mediante hook opcional `window.vyntraAck(...)` y mantiene `window.vyntraError(...)`/flujo legacy.
  - **T03/T05/T08 (parcial, P0 Desktop):** `main.rs` incorpora hash SHA-256 de ROM (`sha2`) y clave de almacenamiento por contenido cacheada por juego (`OnceLock`), rutas de guardado/estado aisladas en `by-id/<hash16>/` con fallback de lectura a rutas legacy por nombre, escritura atómica de SRAM/estados (`atomic_write`) y logging de errores de lectura/escritura de SRAM en lugar de ignorarlos silenciosamente.
  - **T05/sesión Desktop (parcial):** `shell.rs` publica contexto de sesión serializado desde `domain::SessionIdentity` (`session_id`, `game_id` por hash, `rom_sha256`, `core_hash`, `epoch`) junto con `session_epoch`/`command_revision`; genera sesión nueva al lanzar juego y la invalida al detectar el proceso hijo terminado. Falta que el player consuma/valide la sesión end-to-end, manifiestos de guardado, validación runtime y cobertura de todos los flujos de retarget.
  - **T03/catálogo Desktop (parcial):** nuevo `identity.rs` (SHA-256 de contenido, `storage_key`) compartido por player/shell; nuevo `library.rs` con esquema de catálogo (`id`, `path`, `content_hash`, `title`, `system`, `last_seen_unix`), carga compatible con el array legacy de rutas y guardado atómico con backup `.bak`. `shell.rs` usa ese catálogo al importar/cargar y publica `storage_id` estable por juego en el estado de UI.
  - **T08/manifiestos de guardado (parcial):** `main.rs` escribe manifiestos atómicos por tipo en `by-id/<hash16>/` (`manifest.json` tras guardar SRAM, `state.manifest.json` tras guardar estado; no se pisan entre sí), usando `domain::SaveManifest` (kind, bytes, sha256 del artefacto, `core_hash` cacheado por DLL, `state_format` para estados, `created_at_unix`, estado `committed`). Falta manifiesto para exportaciones/copias Companion, validación de recuperación y bloqueo de estados incompatibles por formato/core.
  - **Listado de guardados (compatibilidad):** `save_files` ahora recorre recursivamente las carpetas de saves/states, por lo que los artefactos nuevos en `by-id/<hash>/` siguen visibles/exportables desde la UI.
  - **Catálogo (T03):** el catálogo actualiza `last_seen_unix` y completa hash faltante al escanear, guardando atómicamente solo si hubo cambios.
  - **Sesión IPC (T05):** comandos que incluyen `session_id`/`epoch` se validan contra la sesión activa (`validate_command_session`) y se rechazan con `UiAck` de error si están obsoletos; la UI (`ui/src/app.jsx`) adjunta `session_id`/`epoch` a cada comando cuando hay sesión publicada. Tests unitarios de aceptación/rechazo y de listado recursivo de guardados (19 tests en total).
- Baseline adicional ejecutado: `python scripts/gen_gamedata.py` corrió en esta sesión y regeneró salidas; los archivos generados modificados se revirtieron para no dejar diffs no solicitados (verificación de ejecutabilidad del generador, sin validar equivalencia funcional más allá del comando).
