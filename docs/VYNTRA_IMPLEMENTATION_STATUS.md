# Estado de implementación de Vyntra

Actualizado: 2026-11-17. Este documento registra el comportamiento comprobado del checkout; una función no se considera disponible por aparecer en una imagen de referencia o una etiqueta de interfaz.

## Avance de migración y propiedad de sesión (2026-11-16)

- **T04 parcial:** `desktop-rust/crates/pokedaisy-desktop/src/migration.rs` ofrece preview de solo lectura, journal JSON versionado con copia de respaldo, copia por staging y verificación SHA-256. El Vault permite revisar y aplicar SRAM heredada no ambigua; estados sin identidad quedan bloqueados y los originales se conservan. Tests inyectan `StorageFull` en staging y `PermissionDenied` al copiar `.bak`; subprocesos terminan durante staging de payload y journal, tras instalar destino antes del commit y entre retirar el journal anterior e instalar el temporal. La recuperación verifica hash o `.bak`, conserva el origen, deja el journal previo legible tras un corte de staging y reemplaza el temporal parcial al reintentar. Un save que cambia tras el preview queda en conflicto y nunca instala datos obsoletos. El descubrimiento ya cubre raíces históricas conocidas aunque las carpetas activas sean personalizadas. Faltan cortes en otras fases y otras raíces históricas posibles.
- **T08 parcial:** las acciones Play nuevas usan `storage_id` derivado del contenido y el shell vuelve a resolver ese ID antes de iniciar; el índice numérico queda como compatibilidad con clientes antiguos. El mapeo de teclado SDL configurable hacia `JoypadState` se extrae a función comprobable y tiene prueba de tecla reasignada. El player captura el SHA-256 completo de la ROM y el hash del core al iniciar; antes de guardar manifiestos/saves o restaurar Vault vuelve a comparar la ROM completa con la identidad capturada. Stop explícito termina y recoge el proceso Player cuando el pipe ya no está disponible; una prueba de proceso hijo confirma la terminación y la validación permite Stop tras desconectar la sesión. Una guarda común bloquea nuevas partidas y operaciones Vault/save mientras Player siga activo, conserva el handle en ese caso y limpia handles de hijos terminados; pruebas con procesos reales verifican ambos caminos. Companion recibe mensajes distintos para cierre normal, salida fallida con código y pipe perdido mientras el proceso sigue abierto. El smoke manual mGBA guarda RAM modificada con el flujo normal de batería/manifiesto, valida el hash y la identidad y la restaura al reabrir mediante `open_game`; no reemplaza una sesión completa SDL/Player–Companion.
- **T08 parcial:** fixture con dos ROM distintas llamadas `Same.gb` confirma IDs y destinos SRAM independientes, y que cambiar la selección no reasigna la ROM propietaria de la sesión. Aún no sustituye una prueba de ejecución end-to-end con core.
- **T05 parcial:** F4 valida tipo, estado committed, ROM, hash del core, formato, tamaño y SHA-256. Antes de reemplazar estados o SRAM válidos se crean backups versionados autocontenidos; F4 y el inicio del juego buscan hasta 32 copias recientes si el principal falla e ignoran backups incompletos. Vault exporta/importa ZIP v1 desde UI; la restauración exige la misma ROM y core, obtiene confirmación y crea backup verificado antes de reemplazar. SRAM legacy por nombre solo se carga si todas las ROM con ese nombre comparten el mismo SHA-256 completo; fuentes homónimas que apuntan a juegos distintos bloquean la migración y conservan el archivo. Tests inyectan `StorageFull` y `PermissionDenied` durante staging y fallo de manifiesto después de publicar payload; subprocesos terminan durante staging atómico y entre payload/manifiesto. La recuperación omite el payload sin manifiesto y restaura desde backup verificado sin alterar el archivo comprometido. Faltan ACL/permisos reales y ampliar los cortes de recuperación. Una regresión daña bytes de un payload ZIP y confirma que `decode_bundle` lo rechaza al leerlo. la restauración Vault/SRAM ya se verificó con mGBA local mediante bundle, backup y reapertura, pero la procedencia de esa DLL sigue sin verificar.
- **T06 parcial:** el Core Manager valida cabecera PE, arquitectura y exports sin ejecutar la DLL; una acción explícita lanza un proceso hijo oculto con timeout de ocho segundos para comprobar ABI y `retro_get_system_info`. Tests Windows compilan fixtures C con MinGW y validan GBA, mismatch DS, dependencia ausente, crash aislado y una DLL colgada dentro de `retro_init` que `probe_child` termina al vencer el plazo. No se probó con un core real.
- **T03 parcial:** `inspect.rs` valida cabeceras básicas GB/GBC/GBA/DS con lectura acotada y marca identidad como parcial; reporta checksum de cabecera GB/GBA sin rechazar ROMs por checksum. Tests cubren checksums correctos/dañados y dos ROM idénticas importadas como un solo ID con ambas fuentes retenidas. El catálogo persiste la lista de fuentes y mantiene compatibilidad con entradas legacy. La ROM se rehashea antes de Play. La UI permite elegir la ruta fuente para contenido duplicado; falta corpus amplio de ROMs homebrew/libres por variante/región con licencia verificada.

## Cambios implementados en este checkout

- **T02 parcial:** el shell mantiene una caché acotada de 128 ACK para comandos revisionados. Si se reenvía el mismo comando (revisión, request, sesión/época, acción y payload), devuelve el ACK guardado antes de ejecutar el handler, evitando repetir efectos después de perderse la respuesta. El test cubre replay, otra revisión, comandos legacy y capacidad. La UI ya usa el contrato versionado. No se escriben cuerpos IPC ni rutas absolutas en logs de SRAM; los nombres se limitan a 128 caracteres y los controles se sustituyen. Las cadenas de error del sistema siguen disponibles para diagnóstico.
- **T02 parcial:** el parser exige envelope v1 y rechaza mensajes planos con `missing_protocol_version`; campos extra del envelope, versiones incompatibles, acciones ausentes/desconocidas y payloads inválidos reciben errores estructurados por `window.vyntraAck`. `window.vyntraError` permanece como aviso de frontend. Tests cubren JSON truncado, tamaño, formato plano, acción ausente/desconocida; las acciones se comparan de forma exacta; los payloads validan tipo/campos, enum de filtros/vistas y límites de notas, type chart y ajustes numéricos. IDs de envelope/juego, destinos de carpeta/exportación y campos enumerados también se validan antes del handler; un test ejercita los 27 nombres de acción. No se registran cuerpos IPC; se corrigieron mensajes de Play con codificación dañada y siguen pendientes más revisiones de texto y contexto de rutas en recuperación. La prueba UI offline reconstruye el bundle y valida envelopes/IDs únicos, sesión y payloads anidados.
- **T03 parcial:** además de los fixtures negativos para headers truncados, firma GBA y límites ARM9 DS, una matriz sintética comprueba tres códigos alfanuméricos, revisiones 0/1/255 y checksum válido/dañado sin bloquear inspección. La biblioteca muestra un selector de ruta cuando varias fuentes comparten contenido. `play` lleva `source_index` y `storage_id`; el shell resuelve el índice publicado y valida que conserve la misma identidad de contenido. La UI offline prueba seleccionar una segunda copia y Rust prueba coincidencia y rechazo de índice/identidad obsoletos. Falta corpus de ROMs homebrew/libres por variante/región con licencia verificada.
- **T04 parcial:** la vista previa busca legacy en carpetas configuradas y ubicaciones históricas conocidas bajo `data/saves`, `data/states`, `saves` y `states`, incluso si las rutas activas son personalizadas; no recorre rutas arbitrarias. Tests cubren detección fuera de las rutas activas, origen cambiado desde la vista previa, recuperación del journal desde `.bak`, fallo de instalación y copia de `.bak` denegada sin alterar el journal activo. Procesos hijos terminan durante staging parcial y verificado de payload, staging de journal, tras instalar destino antes del commit y al reemplazar journal activo; el reintento reemplaza el temporal, conserva el origen, verifica destino y usa journal previo o `.bak`, también ante contenido malformado. Faltan cortes en otras fases y otras raíces históricas.
- **T05 parcial:** si falla la escritura del manifiesto tras escribir el nuevo payload en una restauración Vault, la prueba confirma que ambos archivos vuelven a la copia verificada anterior. Además, procesos hijos terminan de verdad durante staging atómico y entre publicar payload y manifiesto: al reiniciar se rechaza el payload sin manifiesto correspondiente y la carga usa el backup verificado. SRAM legacy homónima no se carga ni se duplica durante migración cuando hay más de una identidad de ROM. Faltan ACL/permisos reales; la restauración Vault/SRAM ya se verificó con mGBA local mediante bundle, backup y reapertura, pero la procedencia de esa DLL sigue sin verificar.
- **T06 parcial:** mGBA local declara `0.11-212-7a12d6d` y su SHA coincide byte por byte con el DLL del buildbot oficial Libretro Windows x86_64 descargado en esta auditoría; su alias GBC es la misma copia, no un adaptador distinto. mGBA pasó `probe_child`, cargó `PDTE` por `open_game`, produjo video, completó serialize/unserialize y verificó escritura/lectura de save RAM y restauración Vault. melonDS DS local declara `1.4.0` y cargó `DSPT`, pero no coincide por hash con las variantes oficiales v1.4.0 o el nightly comparados. Una DLL Release oficial v1.4.0, descargada con hash verificado, sí pasó el smoke `DSPT`, video y serialize/unserialize. Las pruebas reales quedan opt-in/ignoradas por defecto; rutas en `VYNTRA_CORE_GAME_SMOKE_PATH`/`VYNTRA_CORE_GAME_SMOKE_ROM`. Evidencia de hashes, versiones y artefactos en `docs/VYNTRA_CORE_PROVENANCE.md`. Falta atribuir el binario melonDS DS local y revisar composición/licencias antes de distribuir.
